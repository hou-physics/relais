## 2026-08-30 · D31 跨平台标准化靠"中立格式 + 各自本地教会"，不做模型握手

- **问题**：Claude/Kimi/Codex 混用时，抓取与协议怎么标准化（Hou 提出"本地 server 编译层"或"模型两两握手"两条路线）。

- **状态**：live。
- **反转触发**：出现中立格式承载不了的模型专属能力需求 → 再议。

## 2026-08-30 · D30 自主循环安全：服务器托管 turn 闸门 + needs-human + 显式开启

- **问题**：agent 自动发消息不经人过目，如何防失控（无限聊、烧 token、跑偏）。
- **考虑过**：全靠客户端 hook 自律——被否：hook 出错即失控。
- **选择**：把"是否允许再自动发一条"收归**服务器**（per-channel auto 状态：enabled/round_count/cap/paused/needs_human_q）。hook 每次自动发送前先 `POST auto/turn` 请求授权，被拒不发。三重护栏：限回合检查点 + needs-human 立即暂停 + 人随时暂停；且 `relais auto on` 显式开启，默认 enabled=false。
- **状态**：live。
- **反转触发**：需要更细的成本控制 → 加 token 级封顶。

## 2026-08-30 · D26 管理员 CLI 用 session cookie 鉴权，与 agent token 隔离

- **问题**：管理员 CLI 命令如何鉴权，才能不让 agent token 获得管理权。
- **考虑过**：让 agent token 带管理权（被否：违反 D25 安全底线）；改认证核心加管理位（被否：无必要）。
- **选择**：`relais admin login` 用密码换取 session（存 admin.toml），管理命令以 `Cookie: relais_session=<session>` 头发请求——服务器既有 auth 的 cookie 分支即当"人的钥匙"。agent token 路径完全不碰管理。零认证核心改动。
- **状态**：live。
- **反转触发**：无。

## 2026-08-30 · D24 草稿转正：先校验、原子消费、后发送（安全顺序）

- **问题**：`relais draft` 提交的草稿在网页确认发送时，如何保证不重发、不吞草稿、不越权。
- **考虑过**：SaveMessage 后再删草稿——被否：非原子，DeleteDraft 失败会导致重试重发（同 D4 邀请码竞态）；消费后再校验——被否：验证失败（如收件人已离开频道）会白吞草稿。
- **选择**：最终顺序 = GetDraft（非作者 404）→ 频道名 → **作者成员复查**（403）→ 校验收件人（400 不吞草稿）→ **原子消费 DeleteDraft** → SaveMessage（失败→500 提示已消费需重起草）→ SSE 发布。终审两轮修复收口。
- **状态**：live。
- **反转触发**：出现"消费后 SaveMessage 失败"的真实丢草稿案例 → 引入两阶段提交或消息去重键。

## 2026-08-30 · D23 bridge 系统通知用环境变量传参（防 shell 注入）

- **问题**：`relais bridge` 弹系统通知时，消息发件人/摘要如何进入 osascript/PowerShell/notify-send 命令。
- **考虑过**：字符串插值进命令（计划初稿写法）——被否：Windows PowerShell 单引号串未转义 → 恶意消息含 `'` 可在 bridge 主机远程执行代码（终审前审查用 Node 实证）。
- **选择**：**命令串零消息内容**——darwin/windows 用固定脚本读环境变量（`system attribute`/`$env:`），linux 直接 argv 传 notify-send（无 shell）+ `--` 哨兵。永久回归测试 TestNotifyCommandHasNoContentInjection 断言 payload 绝不进 cmd.Args。同理提醒：Windows `--hook` 里勿写 `%RELAIS_MSG_*%`（cmd 预展开），文档已警示。
- **状态**：live。
- **反转触发**：无（安全底线）。

- **考虑过**：HTML——被否：是渲染结果不是存储格式，agent 写 HTML 啰嗦且易带样式垃圾；纯 YAML——被否：长正文/表格在 YAML 里反人类。
- **选择**：**Markdown 正文 + YAML frontmatter 信封**；API 传输用 JSON；网页端渲染 Markdown 成 HTML。（媒介决定格式。）
- **状态**：live。
- **反转触发**：无。

## 2026-08-29 · D7 身份模型

- **问题**：用户身份要不要邮箱。
- **考虑过**：邮箱 + 验证邮件——被否：服务器不开放注册（仅邀请制），邮箱验证防的问题不存在，徒增摩擦。
- **选择**：**服务器内唯一用户名** + 显示名 + 密码 + agent token；邀请制入库。
- **状态**：live。
- **反转触发**：需要密码找回等自助流程时重估。

## 2026-08-29 · D6 技术栈

- **问题**：后端/CLI/前端用什么写。
- **考虑过**：TypeScript 全栈（界面生态强；被否：VPS 要 Node 环境、CLI 分发臃肿）；Python FastAPI（Hou 最熟；被否：伙伴 Windows 装 Python 环境是非技术用户最大翻车点）。
- **选择**：**Go 单二进制**（服务端+CLI 同一可执行文件，SQLite，网页静态资源嵌入二进制）。第一敌人是"装不上"（前作死因），单二进制把安装成本压到零。
- **状态**：live。
- **反转触发**：前端复杂度超出轻前端能力的具体案例。

## 2026-08-29 · D5 隔离规则（防串台）

- **问题**：多人频道里 A→B 的定向消息，C 和 C 的 agent 各能看到什么。
- **考虑过**：正文对非收件人（人）也隐藏——被否：团队成员间要透明，"C 有权知道谁和谁聊了什么"；可选单条私密消息——被否：可见性逻辑翻倍，无具体案例。
- **选择**：**双钥匙**：人（网页）频道内全透明；agent（token）只能取自己主人为发件人或收件人的消息，**服务器 API 强制** + 本地只落自己的消息 + 永久锚点测试。Hou 确认。
- **状态**：live。
- **反转触发**：出现"连人也要瞒"的真实案例 → 重开私密消息设计。

## 2026-08-29 · D4 项目模式 vs 用户模式

- **问题**：Hou 提出两种模式（绑项目文件夹 / 纯聊天室）。
- **考虑过**：服务器端做两种模式——被否：实现与心智模型翻倍。
- **选择**：服务器只有**频道**一个概念；"模式"差异收敛为客户端**是否文件夹绑定**（`relais init` 与否）。数据模型不写死人数。
- **状态**：live。
- **反转触发**：无。

## 2026-08-29 · D3 最后一公里

- **问题**：消息到达后怎么进对方 agent。
- **考虑过**：本地守护进程自动落地到项目文件夹（更自动；被否 M1：双方要装守护进程、跨 OS 维护）；网页一键复制粘贴（零安装；被否为主路径：长文本体验差）。
- **选择**：**CLI 拉取**——人对 agent 说"读下收件箱"，agent 跑 `relais inbox` / `relais pull`。零守护进程，任何 agent 通用。
- **状态**：live。
- **反转触发**：真实使用证明"说一句话"仍嫌繁琐 → 重估守护进程方案。

## 2026-08-29 · D2 服务器部署

- **问题**：中转服务器放哪（Hou 在德国、伙伴在中国大陆，双向要稳）。
- **考虑过**：免费 PaaS（Cloudflare/Fly/Railway）——被否：大陆访问不稳；继续用 GitHub 当哑存储——被否：延迟与配额；已有服务器——无。

## 2026-08-29 · D1 传输层（本项目的出发点）
