## 2026-08-30 · D21 项目注册表：init 即注册，bridge 守全部项目

- **问题**：Hou 要求"本地项目文件夹自动接入 + 网页选项目后消息进对应本地文件夹"。
- **考虑过**：网页直接控制本地目录切换——被否：服务器够不着本机，且无此必要——频道即项目，消息按频道落对应文件夹即达成目的；每个项目开一个 bridge 进程——被否：多进程管理负担。
- **选择**：`relais init` 写入全局注册表 projects.toml；单个 `relais bridge` 轮询全部注册频道、消息各落各家。
- **状态**：live。
- **反转触发**：注册表指向已删除目录造成报错骚扰 → 增加自动清理/跳过策略。

## 2026-08-30 · D20 网页三语言（zh/en/de），CLI 暂不 i18n

- **问题**：Hou 要求中/英/德三语、默认跟随系统、可切换。
- **考虑过**：CLI 同步 i18n——被否（本轮）：CLI 主要读者是 agent，中文不构成障碍；工作量转投网页体验。
- **选择**：网页全文案词典化三语 + navigator.language 默认 + header 切换 + localStorage 记忆；join 向导同步。
- **状态**：live。
- **反转触发**：出现非中文使用者需要用 CLI 的具体案例 → CLI i18n 立项。

## 2026-08-30 · D18 M3 本地桥接 relais bridge（部分取代 D3）

- **问题**：Hou 需要"网页/消息到达 → 本地 AI 能被接上"的更自动链路；纯网页用户与"一键喂 AI"都卡在最后一公里。
- **考虑过**：网页直接唤起本地 AI——被否：服务器够不着本机，且自动执行 AI 有安全面；维持纯 CLI 拉取——被否：D3 的反转触发已被真实需求命中。
- **选择**：同一二进制加 `relais bridge` 前台守护：自动拉取落盘 + 系统通知 + 可选 `--hook` 命令（环境变量传消息元数据），只收不发。"一键唤起"由用户自配 hook 实现，工具不预置任何 AI 调用。
- **状态**：live（取代 D3 的"零守护进程"部分；CLI 手动拉取仍保留）。
- **反转触发**：bridge 造成重复落盘/通知骚扰的具体案例 → 重审节流与去重策略。

## 2026-08-30 · D16 网页手动"标记已读"（部分取代 D15）

- **问题**：纯网页用户（如伙伴只用网页版 ChatGPT，无 CLI）永远没有 pull 步骤，未读徽标常亮——D15 的反转触发被具体案例命中。
- **考虑过**：自动已读（看过即清）——仍被否，语义保持"处理过才算"。
- **选择**：每条未读消息加**手动【标记已读】按钮**（调既有 read API）。
- **状态**：live（取代 D15 的"仅 pull 清除"部分；不自动已读的核心语义不变）。
- **反转触发**：无。

## 2026-08-30 · D14 M1 实现与 spec 的已确认偏差（终审记录）

- **问题**：全分支终审比对 spec 逐条后确认的实现偏差，需显式记录以维持 spec 的事实源地位。
- **考虑过**：逐项修掉再合并——被否：均无用户价值紧迫性，M1 验收（§14）不受影响。
- **选择**：以下偏差**有意保留**，排入 M1.x 候选：
  1. join 页列出全部平台下载按钮，未做 OS 自动识别（spec §10）；
  2. 用户模式 `~/relais/<频道名>/` 未实现——CLI 需在已 init 的项目内使用（spec §6）；
  3. CLI 凭证存于 `os.UserConfigDir()`（macOS 为 `~/Library/Application Support/relais/`），非 spec §7 字面的 `~/.config/relais/`；
  4. 落盘文件名为 `日期-发件人-完整ULID.md`（inbox）/`日期-发件人-ULID前10位.md`（sent），非 spec §6 字面的 `序号-发件人-日期.md`；两处命名待统一；
  5. 交叉编译冒烟由 `deploy/deploy.sh build` 手工执行，无 CI（spec §12）；
  6. join 时 CreateUser 的罕见失败（如超长密码触发 bcrypt 错误）会被笼统报为"用户名已被占用"。
- **状态**：live。
- **反转触发**：任一项在真实使用中造成困扰（如伙伴找不到下载按钮、文件名歧义）→ 单独立项修复。

## 2026-08-30 · D15 网页端不做"标记已读"（产品语义）

- **问题**：网页时间线的未读徽标只在 agent `relais pull` 后清除，网页上看过不算已读。
- **考虑过**：网页阅读即标已读（常规聊天软件语义）——被否。
- **选择**：**保留现状为有意语义**：未读 = "尚未喂给 agent 处理"，人只在网页上浏览不消费未读状态。这与"人看摘要、agent 读全文"的分工一致。
- **状态**：live。
- **反转触发**：真实使用中两人反馈徽标常亮造成困扰 → 增加网页手动"标记已读"按钮（不做自动已读）。

## 2026-08-29 · D6 技术栈

- **问题**：后端/CLI/前端用什么写。
- **考虑过**：TypeScript 全栈（界面生态强；被否：VPS 要 Node 环境、CLI 分发臃肿）；Python FastAPI（Hou 最熟；被否：伙伴 Windows 装 Python 环境是非技术用户最大翻车点）。
- **选择**：**Go 单二进制**（服务端+CLI 同一可执行文件，SQLite，网页静态资源嵌入二进制）。第一敌人是"装不上"（前作死因），单二进制把安装成本压到零。
- **状态**：live。
- **反转触发**：前端复杂度超出轻前端能力的具体案例。

## 2026-08-29 · D5 隔离规则（防串台）

- **问题**：多人频道里 A→B 的定向消息，C 和 C 的 agent 各能看到什么。
- **考虑过**：正文对非收件人（人）也隐藏——被否：团队成员间要透明，"C 有权知道谁和谁聊了什么"；可选单条私密消息——被否：可见性逻辑翻倍，无具体案例。
- **选择**：**双钥匙**：人（网页）频道内全透明；agent（token）只能取自己主人为发件人或收件人的消息，**服务器 API 强制** + 本地只落自己的消息 + 永久锚点测试。Hou 确认。
- **状态**：live。
- **反转触发**：出现"连人也要瞒"的真实案例 → 重开私密消息设计。

## 2026-08-29 · D3 最后一公里

- **问题**：消息到达后怎么进对方 agent。
- **考虑过**：本地守护进程自动落地到项目文件夹（更自动；被否 M1：双方要装守护进程、跨 OS 维护）；网页一键复制粘贴（零安装；被否为主路径：长文本体验差）。

- **状态**：live。
- **反转触发**：真实使用证明"说一句话"仍嫌繁琐 → 重估守护进程方案。

## 2026-08-29 · D1 传输层（本项目的出发点）
